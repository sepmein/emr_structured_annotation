# 专用模型与通用大模型：速度分布及业务承载估算

更新：2026-10-09。状态：根据负责人提出的对比图思路形成的展示及测量方案。负责人已确认最终与本地大模型比较，可先用外部模型测试；具体模型、硬件及医院工作量尚未确认。本文没有两类模型的实测差异或实际医院承载结论。

## 已确认的两阶段安排

第一阶段先用外部大模型跑同一批病历抽取任务，完善结构化输出适配，保存预测，比较实体质量及端到端耗时分布，并记录服务版本和调用条件。图上明确标注“本地专用模型 vs 外部大模型服务”；耗时包含各自网络与服务链路，不据此得出同本地算力下的容量倍数。费用或配额有可靠记录时可另作对应预算估算。

第二阶段把确定的通用大模型本地部署，在相同资源预算和任务/质量/覆盖要求下，分别测延迟分布及持续负载吞吐。此时才填“相同算力可支持多少家医院”的规划估算。两个阶段分别保存记录和图表，外部API测量不替代本地大模型实测。

## 汇报页面设计

建议标题：**相同病历抽取任务下的处理效率与业务覆盖潜力**。最终标题中的结论待实测后填写。

页面上方左右各一张“病历长度—完整处理耗时”分布图，中间放关键统计；下方放同等资源下的业务容量情景。

| 左：我们的专用模型 | 中：差异统计 | 右：指定通用大模型 |
|---|---|---|
| 横轴：同一批原文字符数 | 同一批唯一病历数、长度范围 | 横轴：同一批原文字符数 |
| 纵轴：完整有效结果耗时，秒 | 成功请求耗时P50/P95、失败率 | 纵轴：完整有效结果耗时，秒 |
| 散点表示每条病历；颜色表示统一长度分组 | 实测持续有效吞吐、吞吐比值 | 使用相同坐标、颜色和长度分组 |
| 辅助长度分组箱线图或分位数线 | 同一任务的实体质量与全文覆盖 | 辅助长度分组箱线图或分位数线 |

横纵坐标范围须统一；若耗时跨度很大，可对两图同时使用对数纵轴并显式标注。约40条测试任务时直接用散点，避免用平滑密度图制造大量样本的观感；更多独立病历时再考虑二维计数热力图。若显示热力图，两图使用相同网格及颜色计数范围，不各自归一后比较浓淡。

“分布”通过散点聚集、长度分组内的箱线/分位数，以及边缘直方图表达，无需增加第三个空间坐标。输入同一批原文时，两模型的字符长度分布相同，可共享底部长度直方图。读者主要观察：典型请求耗时、较慢请求、耗时随长度的变化、长病历是否失效。

两模型分词器通常不同，因此主图优先用字符数作为共同横轴。补充图可使用同一个明确命名的参考tokenizer计算原文长度；同时分别记录每模型真实输入token、提示词token、输出token及截断/分段情况，不能把两个模型各自的token长度当作天然相同单位。具体大模型输出长度可能影响耗时，不能只记录输入长度。

每条原文重复测量时，主散点使用该病历成功重复请求的耗时中位数，并保留失败次数；全部失败的任务进入单独的失败条带/表，不填成零耗时。重复请求数与唯一病历数分别展示。总体P50/P95按全部正式成功请求计算，并注明口径，与散点的逐病历中位数区分。失败率以全部正式请求计算。

## 中间保留四项主要信息

1. **典型与较慢请求：** 两侧P50、P95及各自比值，另外按共同长度区间展示P95，判断差异是否主要来自短文本。
2. **稳定处理能力：** 同资源预算下，通过响应时限及失败率要求的持续有效吞吐，单位为完整病历/秒。
3. **质量及可靠性：** 同一人工参考下的实体micro F1、关键类别召回率、请求失败率；两者必须完成约定的同一抽取任务。
4. **文本覆盖：** 全文完成率、截断率、分段次数及丢失证据情况，防止只处理部分病历获得速度优势。

中心区域可先展示“P50/P95”“持续吞吐”“质量/覆盖”三组数字，任务数与失败率放在各组下方。质量合格标准、响应时限和可接受失败率由业务要求确定，不在本方案中虚构阈值。

## 测试安排

### 延迟分布实验

先使用相同任务清单，在单并发、每请求一条病历下比较。请求从客户端发送前开始，到完整抽取结果接收、解析及结构校验结束；两边计时范围一致。大模型须输出同一标签体系的结构化抽取结果，而非自由问答，计时不能在首个token出现时结束。NER与NER+RE的任务范围需一致或分开列出。

可直接沿用实体评价测试集同时评价质量与耗时。若为覆盖长文本、医院高峰补充了更大批次，应单独登记来源、长度分布和是否有人工参考；没有人工参考的负载请求只能说明运行能力。不得按观察到的速度或效果挑选有利测试病例。

模型加载与冷启动单列；预热不进入正式样本。交替安排运行顺序，记录服务器其他负载、缓存、批量、并发、模型精度、硬件、显存及版本。重复病历或共同提示前缀可能命中缓存，须控制并披露缓存策略。

### 持续承载实验

另做逐步增加并发/请求到达率的实验，保存持续阶段的完整结果、墙钟时间、P95及失败率，检查队列是否持续增长。容量Q取满足预先约定时限、失败率和覆盖要求、且队列稳定的一档实测完整病历吞吐，不能使用瞬时峰值，也不能用`1/P50`替代。

质量通过相同人工参考的独立评价确认；“有效请求”在测速中表示输出结构有效且满足约定覆盖，不表示其所有实体医学上均正确。吞吐分母保留失败请求占用的时间；若约定生产重试，重试消耗也须计入容量，单列唯一病历与请求次数。

相同硬件预算的容量比较允许各模型使用适合自身的并发/批量配置，但须透明记录，并满足相同任务、质量、覆盖及响应要求。另保留同一并发的延迟分布实验，不能把两类不同实验的结果混在一个提速数字中。

### 比较资源的边界

- 同一资源预算本地部署：可估算在这套硬件上两个方案各自的病历容量。若大模型无法装入该硬件，记录资源不足，改用可运行的等预算方案或分别报告资源，不虚构其速度。
- 两边硬件不同：先报告部署实测，再按明确的资源/成本预算规划，不能只按GPU张数线性换算。
- 外部API：可比较端到端耗时、费用及配额下的业务容量；不能据此声称“相同本地算力扩大多少倍”。

## 从吞吐估算医院承载

输入必须具有明确来源：Q为实测持续有效吞吐，H为每天可用处理小时，a为规划可用比例/余量系数，V为每家医院每日进入本任务的病历量，λ为每家医院的高峰病历到达率，k为每病历实际需要的抽取调用数。使用a时说明其覆盖的维护/突发余量，避免把已经实测扣除的失败或已经保留的相同余量再次扣除。长病历分段和重试若已包含在完整病历Q中，不能再次用k重复折算。

以Q按“完整病历/秒”计、单次全流程已经包含必要分段/重试为例：

```text
每日规划容量 C = Q × 3600 × H × a
按每日总量可支持的医院数 N_day = floor(C / V)
按高峰可支持的医院数 N_peak = floor(Q × a / λ)
规划医院数 N = min(N_day, N_peak)
吞吐比值 R = Q_我们的模型 / Q_对照模型
```

若记录的是调用/秒，应先除以每病历平均调用数k；k受病历长度分布影响。不同医院工作量不相同时，改用各院每日总量及可能同时出现的峰值之和，不使用统一V或λ掩盖差异。医院数是模型处理环节的规划值，真实上线还受数据接入、网络、复核人员和其他流程限制。

先用业务病历长度分布的混合负载实测整体Q。仅有分长度桶的Q时，在相同计时及并发口径下按每桶处理时间加权作近似，不能把吞吐率直接算术平均；近似结果仍需混合负载验证。

### 仅用于解释计算的假设情景

下表数字全部是假设，既非本项目实测，也不代表任何具体通用大模型或医院。假定两方案同一硬件预算、满足相同任务及质量要求，日处理8小时，规划比例70%，每院每日需处理2万条病历。

| 项目 | 假设通用大模型 | 假设我们的模型 |
|---|---:|---:|
| 持续吞吐 | 1条/秒 | 10条/秒 |
| 每日规划容量 | 20,160条 | 201,600条 |
| 只按每日总量估算的医院数 | 1家 | 10家 |

这一假设下吞吐为10倍，按总量估算由1家到10家、增加9家；尚未加入高峰约束，不能写成已证明可承载10家医院。正式材料用实测Q和业务V、λ替换数字，并附计算依据、规划余量及适用边界。不要用“提升10倍”混淆“达到原来的10倍”与“增加900%”。

已实现[配对测速记录对照与制图工具](../../scripts/compare_model_benchmarks.py)：生成统一散点、共同长度直方图、差异统计、失败任务表及可选容量情景图；仅用虚构记录完成演示。[Chat Completions大模型适配入口](chat-model-benchmark.md)已补齐结构化抽取、首轮原始预测及API usage记录，完成模拟验证。后续需联调指定真实服务，补齐双方真实原文token/分段覆盖、并发及到达率测试。主比较至少留存下列记录：

| 类别 | 需保留字段 |
|---|---|
| 对照与来源 | 运行ID、模型产物/服务版本、任务清单校验值、唯一任务ID |

## 制图工具：已经跑通的虚构示例

工具读两个具有同一输入清单SHA256的测速JSON，要求任务ID、字符数相同，每条任务每轮都有明确成功或失败记录。它重算全部统计，不信任输入中已有的P50或吞吐摘要。计时范围、并发或重复设计不一致时仍列两侧统计，但不计算延迟比值；两侧成功的任务/轮次集合不同时也不计算比值，避免不同失败病例改变成功样本分布。未知token/截断信息不能自动变为已覆盖。

分析和JSON/Markdown输出仅需Python标准库；`--plot`需要运行环境已安装Matplotlib，生成PNG及SVG，供汇报插图使用。不会安装依赖、启动模型或发起请求。`--log-y`把两侧同时改成明确标注的对数纵轴；成功中位数为0或没有成功记录时拒绝对数绘图，仍可改用线性轴。每次使用新输出目录，图形失败不会发布半成品目录。

```powershell
python scripts/compare_model_benchmarks.py `
  --ours tests/fixtures/model_benchmark_plot_demo/ours.json `
  --baseline tests/fixtures/model_benchmark_plot_demo/baseline.json `
  --context tests/fixtures/model_benchmark_plot_demo/context.json `
  --plot --log-y --output-dir output/model_benchmark_plot_demo
```

查看[分布图PNG](../evaluation_examples/model_benchmark_plot_demo/latency_distribution.png)、[可缩放SVG](../evaluation_examples/model_benchmark_plot_demo/latency_distribution.svg)、[统计与失败表](../evaluation_examples/model_benchmark_plot_demo/comparison.md)及[完整点位/来源校验值](../evaluation_examples/model_benchmark_plot_demo/comparison.json)。共12个虚构任务ID，每侧3轮、36次虚构请求记录；本工具和样例没有实际调用任何模型。

这里的[输入清单](../../tests/fixtures/model_benchmark_plot_demo/fictional_length_manifest.json)仅包含虚构ID与长度元数据，不含可用于真实测速的病历原文。两侧耗时、失败和版本全部人工构造，且不与20条Label Studio格式演示混称为同一批数据。本示例包含一侧全部失败的长文本，用于检查图顶端的失败标记；成功样本不同，因此延迟比值为“—”。图形本身不能证明短文本、长文本或任何模型的实际能力。

实际记录可分别使用[专用模型测速客户端](model-service-benchmark.md)及[大模型测速客户端](chat-model-benchmark.md)产生相同逐次字段及任务文件来源绑定，两者均需真实服务验收。准备单独的`context.json`明确名称、部署位置及同一抽取范围：

```json
{
  "ours": {"label": "我们的模型", "deployment": "local", "task_scope_id": "reviewed_ner_re_v1"},
  "baseline": {"label": "指定外部模型服务", "deployment": "external_api", "task_scope_id": "reviewed_ner_re_v1"}
}
```

其中任务范围是操作者声明，不是工具证明。不能给只做NER的服务与NER+RE服务填写相同范围以掩盖差异。输入元数据、服务返回版本及校验值同样不能替代权重、硬件与质量核实。

### 可选容量情景

容量必须另供`--capacity-scenario`。两侧均声明`local`、且明确相同非空`resource_budget_id`时才允许同资源医院情景；外部API比较会拒绝该参数。输入明确的完整病历持续吞吐、每日时窗、规划比例、医院日量及高峰，输出取日总量限制与高峰限制中较小的医院数；不会使用图中单并发吞吐或延迟比值自动推算。

使用[虚构本地配置](../../tests/fixtures/model_benchmark_plot_demo/local_context.json)及[全部是假设的容量输入](../../tests/fixtures/model_benchmark_plot_demo/capacity_scenario.json)，可复现[容量情景图](../evaluation_examples/model_benchmark_capacity_demo/latency_distribution.png)和[计算表](../evaluation_examples/model_benchmark_capacity_demo/comparison.md)。命令在上述演示基础上替换`--context`、增加`--capacity-scenario`并改用新的输出目录。

输入中的复核声明只模拟操作，未执行真实质量复核或持续负载测试。输出始终标为`assumption_based_planning_only`，既不认证声明，也不声称业务验收。正式使用时保留真实负载记录和业务假设依据，区分实测吞吐与规划容量。

验证见[离线测试](../../tests/test_compare_model_benchmarks.py)，覆盖任务/轮次绑定、失败分母、摘要重算、成功样本不一致、不同计时条件、混合版本、外部API容量拒绝、峰值约束、输入数值及结果覆盖保护。另实际运行PNG/SVG导出并检查图形；这不是模型性能测试。

测量口径参考：[vLLM官方Benchmark CLI](https://github.com/vllm-project/vllm/blob/main/docs/benchmarking/cli.md)分别记录请求吞吐、输入/输出token及不同延迟，并说明客户端计时边界与缓存影响；本文提出的医院容量公式是基于明确业务假设的规划计算，不是该文档提供的医院实证结果。
