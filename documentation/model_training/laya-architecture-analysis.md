# 当前多任务模型与Laya架构分析

本页为2026-10-11代码与公开资料核查。事实、试验结果和建议分开；没有安装Laya、调用外部推理API或宣称复制Jev私有实现。分析针对本轮离线Schema多任务模型，原Label Studio在线后端尚未接入这些属性/融合头。

## 当前实现和属性支持

入口为`modernbert_ml_backend/modeling/schema_multitask.py`与`training/schema_experiment.py`。mmBERT产生token上下文，低秩起止跨度头预测49类实体；实体表示拼接起点、终点、跨度内均值和实体类型，投影到256维。每个perRegion属性有独立线性分类头，当前共9个：存在状态、时间、病程、条件、假设、主体、检验结果、标本类型、检测方式。关系头读取两个实体表示及中间文本均值；额外CLS头预测病例四分类。

转换层按相同region id匹配实体与Choices，检查适用实体标签和别名；训练只对已经标注的有效属性槽位计算交叉熵，空白不转成阴性。推理时将适用属性挂在对应实体的attributes下，同名病原体在不同位置保留不同实体id。字符边界修正和同类重叠抑制是本轮新增实验选项，不改变原Schema。

症状/诊断的五轴属性以及选填病程变化均已训练和预测。病原体的test_result、specimen_type、detection_method也均已训练和预测。但后续临床证据向量目前显式读取断言状态与检验结果，**没有显式编码标本类型、检测方式及两者与结果的组合**。文本向量可能包含这些信息，不等于结构特征已经保留。本轮检出辅助输出还聚合为4个分组，会丢失21个病原体与不同检测记录之间的细节。

当前pneumonia_config.xml还含“抗体IgG”；本次粘贴的片段没有这一项。冻结数据与既有训练继续保留完整Schema，不按片段删除类别。

## 已完成开发评估如何解释

`evaluation/run_modular_002`是验证F1更高的第二轮抽取器；测试NER F1为76.44%。第一轮修正抽取器验证87.12%、测试78.75%；第二轮验证88.68%、测试76.44%，说明小验证集的选择未稳定外推。两轮均优于原抽取器测试64.09%，但都未达实体80%—85%。病例验证选中的分层融合头测试macro F1为59.00%，原融合头67.42%；未按测试表现改选其他分支。

第二轮检测属性在已知参考槽位上的端到端正确比例为：test_result 107/117=91.45%、specimen_type 114/117=97.44%、detection_method 114/116=98.28%。三项全部有参考的116条实体检测记录中，字符跨度、实体类型及三项属性同时正确106条（91.38%）。这些是已知槽位/记录正确比例，不是完整预测检测记录F1。

标本参考116条为“原文未说明”、仅1条为“血液(未说明采样间隔)”；始终选未说明的参考占比99.15%。因此标本97.44%不能证明具体标本识别能力。检测方法有抗体IgM 80、抗原快速检测22、核酸13、IgG 1，没有mNGS、培养、双份抗体等真实支持。检验结果阳性7、阴性100、无法判断10；阳性仅1/7正确（14.29%），其余6条被判成阴性，阴性96/100正确、无法判断10/10正确。总体91.45%掩盖了阳性识别不足。新审计清单记录每个选项的支持、正确数、漏失实体和联合正确比例：`delivery/run_optimization_001/pathogen_attributes.json`。

训练参考同样不均衡：128例真实训练中的检验结果为阴性257、阳性20、无法判断32；标本295个未说明，具体标本只有拭子1、痰4、尿2。1000条合成病例包含750处病原检测属性，但标本全为“痰”、方法全为“核酸检测”；三种检验结果各250。当前合成数据不能提供mNGS、灌洗液、血液间隔等属性组合的训练多样性。类别不均衡和模板分布是需要通过消融验证的可能原因，不能仅凭这些计数断定模型误差的唯一原因。

## Laya：哪些事实可核实

项目：[NandhaKishorM/laya](https://github.com/NandhaKishorM/laya)，本次固定源码commit `68804629e8ccd9d616d48a40e87de9fabbeae069`。源码及哈希留在`research/run_laya_001/source_commit.json`，仅下载审查文件，没有执行第三方代码。

1. [common.py](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L225)把问题指令、候选答案文字及MASK标记构成输入。DecisionModel在双向编码器上增加Transformer决策层，对候选标记使用共享评分器；可表达choice、score、noul。其输出槽位由请求中的选项文字定义，与本项目固定字段Linear输出不同。
2. [DecisionModel](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/common.py#L574)还含题型嵌入与动作头。共享状态的tokenization与批处理不等于所有独立问题都共享同一条已经编码的隐藏序列；不能把“一次调用”直接说成整例所有实体属性只经过一次编码器。
3. [训练实现](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/train.py)支持soft-ce及rlcd；后者包含噪声logit采样的奖励项和软标签交叉熵。源码说明其特定typed-decisions划分上未观察到额外奖励项的收益，不能认定RLCD必然优于交叉熵。
4. [校准实现](https://github.com/NandhaKishorM/laya/blob/68804629e8ccd9d616d48a40e87de9fabbeae069/laya/calibrate.py)提供温度拟合，支持数很少时提示证据不足。校准主要改变概率可靠性；统一正温度通常不改变同一分类头的argmax，不能把它当作必然提高F1的方法。
5. 作者README公开多语言检查点以mmBERT-base为编码器；公开性能是其自己的任务、硬件与数据。不能外推到本项目中文病历或给本项目承诺同等延迟/F1。

TypeSafe官方将[Jev](https://docs.typesafe.ai/introduction)定义为对共同状态做并行类型化判断的模型，强调概率与置信度。[发布材料](https://typesafe.ai/blog/introducing-system-one-models-and-jev)介绍RLCD，但未给出足以重建内部网络和完整训练的细节；Laya源码可作为独立公开实现参考，不能认定它就是Jev的实际内部架构。

## 建议改进顺序

第一步保留当前mmBERT-base和实体定位头，把全部适用属性传入后续模型。检测记录以“病原实体id/字符位置＋结果＋标本＋检测方式”为单位；相同病原体不同位置不先合并成单个阳性。保留未知和原文未说明状态，病原检出与致病原因分开。

第二步借鉴Laya的问题条件机制与PURE实体标记：对每个实体生成明确的字段查询，例如“这处流感病毒记录的检测方式是什么”。属性表示结合实体位置、局部句段、字段及候选值，而不是只用256维实体表示做独立Linear。为控制计算，可以设计共享全文token表示＋实体/字段查询attention，而非照搬每个属性重复编码整篇病历。先用原监督交叉熵、少量参数/adapter，比较现有头与查询头。

第三步加强数据与属性损失：补充具体标本、不同方法、阳性/阴性同句、同一病原体重复检测、不同样本/方法结果冲突等真实参考，合成样本增加受Schema约束的属性组合并作为训练对照。按字段的真实训练频数比较加权交叉熵、阳性均衡采样与原损失，权重上限和合成比例只在验证集选；没有支持的类别不能靠无限放大权重解决。没有关联监督时，不能默认把同段所有方法与结果挂到最近的病原体。若一处实体需要多次检测记录，现有单值perRegion Schema不够，需另设计带记录id的检测事件结构；属于未来Schema变更，不能静默改写冻结数据。

第四步分层验收：实体严格F1；各属性逐值支持与macro F1（先明确缺失/未知分母）；完整检测记录联合严格匹配；病例macro F1；概率校准与选择性复核覆盖率。对本轮稀少标本/方法只报告不可充分评价，不用总体98%代替关键类别能力。增加独立校准数据后再拟合温度和复核阈值；“待专业复核”是真实标签，模型置信度是另一个维度。

这些查询头、全检测特征和校准是设计建议，尚未实现或训练；本轮已实施的边界修正、负例/权重调整、分层分类和LR/XGBoost对照另见优化报告。
