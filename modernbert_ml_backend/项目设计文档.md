## 1. 目标、边界与术语

### 1.1 目标

本项目将本地中文 ModernBERT 封装成 Label Studio ML Backend，在一个共享文本编码器上同时完成以下任务：

1. **NER（命名实体识别）**：为每个 token 预测 BIO 标签，输出原文字符区间的实体。
2. **RE（关系抽取）**：基于已识别实体对，预测关系类别或“无关系”。
3. **训练闭环**：从 Label Studio 拉取已完成标注，在本地训练 LoRA 适配器和任务头，保存后立即重载用于预测。

模型标签不在代码中硬编码。服务从 Label Studio `label_config` 提取实体、关系标签，按标签集合产生 schema ID，并将微调产物按 schema 隔离，避免把不匹配的分类头用于不同项目。

### 1.2 非目标与实现边界

- 不提供生成式问答、跨文档实体消歧或通用知识推理。
- 默认离线运行：基础模型和 tokenizer 必须预先放入 `bert-base-model`，不会自动从 Hugging Face 下载缺失文件。
- 未实现异步训练任务队列；当前训练由 webhook 请求同步触发。
- 未实现多进程共享模型缓存或动态 Token 存储。
- 不将 Label Studio Token 写入 `.env`、SQLite、训练产物或挂载卷。

### 1.3 名词

| 名词 | 含义 |
| --- | --- |
| Token / offset mapping | Tokenizer 切分文本后的子词及其原文字符区间 `[start, end)`。它使 token 级预测可回写为 Label Studio 字符偏移。 |
| BIO | `B-X` 为 X 类型实体开头，`I-X` 为内部 token，`O` 为非实体。 |
| 有序实体对 | `(实体1, 实体2)` 与 `(实体2, 实体1)` 是不同 RE 候选。 |
| LoRA | Low-Rank Adaptation；冻结原权重，只学习低秩增量矩阵。 |
| schema ID | 对实体与关系标签列表规范化 JSON 做 SHA-256 后取前 12 位，例如 `schema_0123abcdef45`。 |
| `best_model` | 某 schema 下用于推理的最佳训练产物目录。 |

## 3. 基础模型与联合网络原理

### 3.1 Chinese ModernBERT

本地配置文件显示基础模型是 encoder-only ModernBERT：28 层、隐藏维度 1024、16 个注意力头、32,979 词表、最大 8,192 token。单头维度约为 `1024 / 16 = 64`。

ModernBERT 交替使用局部和全局注意力。`local_attention=128` 的局部层只在相邻窗口中计算注意力，计算量近似随 `序列长度 x 128` 增长；每三层出现的全局注意力层建立跨窗口依赖。它兼顾长文本效率与全局语义建模。RoPE 将位置信息旋转编码进 Query/Key 向量；局部和全局层使用不同的 RoPE theta。

该中文模型预训练使用 BPE 词表与动态 Whole-Word Masking。WWM 会共同掩盖一个词的子 token，迫使 encoder 使用上下文学习词级语义。微调阶段复用这些通用文本表征，只训练任务相关的低秩适配器和分类层。

### 3.2 共享编码器

给定 token 序列 `x=(x1,...,xL)`、注意力掩码 `m`，编码器输出：

```text
H = ModernBERT(x, m),  H 的形状为 [L, 1024]
```

NER 与 RE 共用 H。这让实体识别和关系分类围绕同一上下文表征学习，也减少相对于两个独立模型的内存与加载成本。

### 3.3 NER 分类头与 BIO 解码

NER 头是每 token 的两层 MLP：Dropout -> Linear(1024,1024) -> GELU -> LayerNorm -> Dropout -> Linear(1024,标签数)。输出 logits 经 softmax 得到标签分布。

NER 标签映射固定以 `O: 0` 开始；若有 N 种实体，则类别数是 `1 + 2N`，每种实体对应 `B-类型` 与 `I-类型`。解码使用贪心 argmax，而不是 CRF：

1. `B-X` 开启实体 X；
2. 紧随的 `I-X` 延长该实体；
3. `O`、不匹配类型的 I 标签、新的 B 标签结束当前实体；
4. 相邻或重叠且同类型的实体会合并；
5. 实体置信度取该实体内各 token 被选中标签概率的平均值，低于 `NER_THRESHOLD` 即删除。

贪心解码速度快，但没有 CRF 的全局转移约束，因此 BIO 边界质量高度依赖标注一致性、数据量和阈值校准。

### 3.4 RE 分类头与距离特征

对于有序实体对 `(e1,e2)`，模型对实体 token 表征做均值池化得到 `r1`、`r2`，再将带符号 token 距离映射为距离向量 `d`：

```text
r = concat(r1, r2, d)              # 形状 [3 x 1024]
relation_logits = MLP_RE(r)
```

模型内部距离绝对值上限是 128 token，超出的距离会裁剪；正负号保留实体相对方向。距离嵌入让模型学习位置先验，例如相邻实体通常比相隔很远的实体更可能存在关系。

推理仅在已通过 NER 阈值的实体间枚举候选，并跳过同一实体类型的组合。候选数最坏为 O(E^2)，E 为保留实体数。关系类别 0 固定为“无关系”；只有预测不是 0 且概率达到 `RE_THRESHOLD` 时才输出。最后还会以 `RE_MAX_DISTANCE` 按**原文字符距离**过滤。注意：128 是模型内部 token 距离，`RE_MAX_DISTANCE` 是结果层字符距离，两者不可直接等同。

### 3.5 联合损失与类别不平衡

训练总损失为：

```text
loss = ner_loss_weight * CrossEntropy(NER) + re_loss_weight * CrossEntropy(RE)
```

padding token 的 NER 标签为 `-100`，由 `ignore_index=-100` 排除。默认将 NER 的 `O` 类和 RE 的“无关系”类权重降低到 0.15，减少大规模负类对优化的支配。训练器还按实体标签频次计算 NER 权重，默认采用平方根反频率：`1 / sqrt(count / avg_count)`，并限制到 `[0.5,5.0]`，使稀有类型得到提升而不致产生极端梯度。

### 3.6 LoRA 原理

原始线性层权重 W 冻结，LoRA 训练低秩矩阵 A、B：

```text
W_effective = W + (alpha / r) * B * A
```

当前默认 `r=16`、`alpha=32`，缩放为 2，目标模块为 `Wqkv`、`Wo`、`Wi`，分别覆盖注意力 QKV 投影、注意力输出投影和前馈投影。`lora_dropout=0.1` 对 LoRA 分支正则化。

NER/RE 头和距离嵌入不是 LoRA 参数，仍为普通可训练模块。因此恢复 LoRA 模型时除了 adapter 文件，还必须加载 `classification_heads.pt`；单独复制 `adapter_model.safetensors` 不足以完成任务推理。

## 4. 训练设计

### 4.1 标注转换

已完成、未取消的 Label Studio 任务会转换为：

```json
{
  "text": "患者服用阿司匹林后出现皮疹",
  "entities": [{"id":"e1","start":2,"end":7,"label":"药物"}],
  "relations": [{"from_id":"e1","to_id":"e2","type":"不良反应"}]
}
```

Tokenizer 使用 `return_offsets_mapping=True`、截断和 `MAX_LENGTH`。字符区间与 token offset 有交集的 token 被赋予 B/I 标签。当前 `_generate_ner_labels()` 以 `O=0` 初始化所有位置，因此特殊 token 的 `(0,0)` offset 会保留为 `O`；只有 `collate_fn` 为批内动态 padding 新增的位置会填充 `-100`。Tokenizer 以 `do_text_preprocessing=False` 加载，避免预处理改变字符串而导致 Label Studio 的字符偏移失真。

#### 4.1.1 数据、实体、关系与标签 ID 的完整映射示例

以下示例使用同一条原文贯穿 Label Studio 标注、训练集转换、token 标签和预测回写。token 表采用逐字切分的**示意** offset；实际 BPE tokenizer 可能合并连续字符，但映射规则完全相同。

原文：

```text
患者服用阿司匹林后出现皮疹
0123456789012
```

“阿司匹林”的字符区间是 `[4,8)`，即 `text[4:8] == "阿司匹林"`；“皮疹”是 `[11,13)`。右边界不包含在实体中。

**Label Studio 标签到模型标签 ID**。假设标签配置中的实体顺序为“药物、症状”，关系类型为“不良反应”，动态标签映射如下：

| Label Studio 标签 | 任务 | 模型标签 | ID | 含义 |
| --- | --- | --- | --- | --- |
| 无实体 | NER | `O` | 0 | 非实体 token。 |
| 药物 | NER | `B-药物` | 1 | 药物实体第一个 token。 |
| 药物 | NER | `I-药物` | 2 | 药物实体后续 token。 |
| 症状 | NER | `B-症状` | 3 | 症状实体第一个 token。 |
| 症状 | NER | `I-症状` | 4 | 症状实体后续 token。 |
| 无关系 | RE | `无关系` | 0 | 有序实体对不存在标注关系。 |
| 不良反应 | RE | `不良反应` | 1 | 药物指向症状的关系。 |

标签顺序也是 schema 的组成部分。把“症状”放到“药物”之前会改变 BIO ID 与 schema ID，必须训练或加载新 schema 目录中的产物。

**Label Studio annotation 到内部训练样本**。原始任务的关键字段可表示为：

```json
{
  "data": {"text": "患者服用阿司匹林后出现皮疹"},
  "annotations": [{
    "was_cancelled": false,
    "result": [
      {"id":"ls_drug_1", "type":"labels", "value":{"start":4,"end":8,"text":"阿司匹林","labels":["药物"]}},
      {"id":"ls_symptom_1", "type":"labels", "value":{"start":11,"end":13,"text":"皮疹","labels":["症状"]}},
      {"type":"relation", "from_id":"ls_drug_1", "to_id":"ls_symptom_1", "labels":["不良反应"]}
    ]
  }]
}
```

解析器第一次遍历只建立实体和 `entity_id_map`，第二次遍历 relation，确保两端 ID 都存在。内部训练样本为：

```json
{
  "text":"患者服用阿司匹林后出现皮疹",
  "entities":[
    {"id":"ls_drug_1","start":4,"end":8,"text":"阿司匹林","label":"药物"},
    {"id":"ls_symptom_1","start":11,"end":13,"text":"皮疹","label":"症状"}
  ],
  "relations":[{"from_id":"ls_drug_1","to_id":"ls_symptom_1","type":"不良反应"}],
  "has_relations":true
}
```

`ls_drug_1` 和 `ls_symptom_1` 是 Label Studio 标注关联 ID，不是 BIO/RE 分类 ID，也不是最终预测响应里的 `ent_0`。

**字符 offset 到 BIO 标签 ID**。token 与标签映射如下：

| token 下标 | token | offset | 相交实体 | BIO | ID |
| --- | --- | --- | --- | --- | --- |
| 0 | `[CLS]` | `[0,0)` | 无 | `O` | 0 |
| 1-4 | 患、者、服、用 | `[0,1)` 至 `[3,4)` | 无 | `O` | 0 |
| 5 | 阿 | `[4,5)` | 药物 `[4,8)` | `B-药物` | 1 |
| 6-8 | 司、匹、林 | `[5,6)` 至 `[7,8)` | 药物 `[4,8)` | `I-药物` | 2 |
| 9-11 | 后、出、现 | `[8,9)` 至 `[10,11)` | 无 | `O` | 0 |
| 12 | 皮 | `[11,12)` | 症状 `[11,13)` | `B-症状` | 3 |
| 13 | 疹 | `[12,13)` | 症状 `[11,13)` | `I-症状` | 4 |
| 14 | `[SEP]` | `[0,0)` | 无 | `O` | 0 |

对应 `ner_labels`：

```text
[0, 0, 0, 0, 0, 1, 2, 2, 2, 0, 0, 0, 3, 4, 0]
```

实体与 token 只要部分相交即匹配，即满足 `token_start < entity_end and token_end > entity_start`。此规则避免 BPE token 跨实体边缘时遗漏边界 token。

**实体 ID 到 RE 训练对**。同一转换产生：

```text
entity_token_map = {
  "ls_drug_1":    (5, 9),
  "ls_symptom_1": (12, 14)
}
```

正例关系被转换为 `((5,9),(12,14)) -> 1`。训练负采样与预测候选策略不同：训练会对每个实体最多随机取 3 个未标注目标，且包含同类型实体对。本例只有两个实体，因而会确定地加入反向负例：

```text
entity_pairs = [((5,9),(12,14)), ((12,14),(5,9))]
re_labels    = [1, 0]
```

这说明关系方向是数据的一部分：药物 -> 症状被标为“不良反应”，并不代表症状 -> 药物也是该关系。

### 4.2 关系样本与负采样

真实标注关系直接形成正样本。未被标注的实体对是“无关系”候选，训练器从中进行负采样，避免 O(E^2) 无关系组合压倒有限正例。实体因截断无法映射到 token 时，相应关系无法参与训练；数据治理应检查文本长度和关系两端实体是否完整保留。

### 4.3 Batch、优化和验证

| 环节 | 当前行为与原理 |
| --- | --- |
| Dynamic padding | 每个 batch 只填充到本批最长序列，不固定填充到 `MAX_LENGTH`，减少无效计算和显存。 |
| 设备 | CUDA 时启用 autocast/GradScaler；CPU 使用普通精度训练。 |
| 梯度裁剪 | `max_grad_norm=1.0` 限制梯度范数，降低异常梯度导致训练不稳定的风险。 |
| 优化器 | AdamW；encoder/LoRA 用 `learning_rate`，随机初始化的分类头和距离嵌入可用较大的 `classifier_lr`。 |
| 调度 | 总步数前 `warmup_ratio` 线性 warmup，之后线性衰减，避免初始更新破坏预训练表征。 |
| 划分 | 大于 20 条时随机种子 42 打乱后按 80/20 划分；不大于 20 条全部训练、无验证集。 |
| 少样本 | 训练样本小于 30 条时随机打乱后过采样至 30 条，仅为稳定训练步数，不能替代新增标注。 |
| 早停 | 综合 F1 未超过 `early_stopping_min_delta` 的轮数达到 `early_stopping_patience` 时终止。 |

### 4.5 端到端训练详细过程

以下过程描述一次由 Label Studio 发起的 `START_TRAINING` 到新模型可用于预测的完整调用链。当前实现是同步调用：在训练完成、失败或提前返回前，`/webhook` 请求不会结束。

```text
Label Studio START_TRAINING webhook
  -> ModernBERTModel.fit()
  -> 校验事件 / 动态 Token
  -> Label Studio SDK 拉取已标注任务
  -> 任务标注转换为 text + entities + relations
  -> 固定随机种子，划分/过采样训练集
  -> tokenizer offset 对齐，生成 BIO 和 RE 标签
  -> DataLoader 动态 padding
  -> LoRA/分类头初始化或恢复 checkpoint
  -> epoch 循环：前向 -> 联合损失 -> 反向 -> 裁剪 -> optimizer/scheduler
  -> 验证、保存最佳权重、早停
  -> 清理 LRU 缓存并从 best_model 重载
```

#### 步骤 1：训练事件与先决条件

`ModernBERTModel.fit(event, data)` 首先精确匹配 `event == "START_TRAINING"`。`ANNOTATION_CREATED`、`ANNOTATION_UPDATED`、`ANNOTATION_DELETED` 虽会进入 HTTP webhook 路由，但业务层直接跳过，不产生训练。

随后调用 `_load_training_data()`：

1. 通过项目 ID 从内存 Token 字典取出最新 `/setup` 下发的 `access_token`；缺失时记录告警并返回空列表。
2. 用 `LABEL_STUDIO_URL` 和该 Token 创建 Label Studio SDK 客户端；地址不可达或 SDK 初始化失败时返回空列表。
3. 调用 `tasks.list(project=项目ID, only_annotated=True, fields="all")` 拉取任务。
4. 过滤所有 annotation 都标记为 `was_cancelled=true` 的任务。
5. 逐条解析，只有含有至少一个实体的样本会进入训练集合；只带关系但没有实体的异常数据不会参与训练。

因此，训练前必须已通过 `/setup`，Label Studio 对容器可达，并且项目存在非取消状态的实体标注。任何一个条件不满足都会使训练“成功返回但未训练”，原因记录在后端日志中。

#### 步骤 2：Label Studio 标注解析

对每个任务，代码选择第一份非取消且包含 `result` 的 annotation。解析分两次进行，以允许 relation 引用前面/后面的实体：

1. 遍历 `type="labels"` 的结果，从 `value.labels[0]`、`value.start`、`value.end`、`value.text` 读取实体，使用 Label Studio result 的 `id` 作为实体 ID；同时建立 `entity_id_map`。
2. 再遍历 `type="relation"` 的结果，读取 `from_id`、`to_id` 和 `labels[0]`。只有关系两端 ID 都能在 `entity_id_map` 找到时才保留。
3. 返回 `text`、`entities`、`relations` 和 `has_relations`。如果标签在动态 schema 映射中不存在，代码会记录 warning，但不会在这一层立即丢弃数据。

字符区间采用左闭右开约定 `[start, end)`：`text[start:end]` 必须等于标注的实体文本。标注工具、文本预处理或导入过程改变原文后，offset 不一致会直接影响训练标签和预测回写。

#### 步骤 3：训练/验证拆分与小数据处理

`train_from_data()` 将随机种子设为 42，调用 `random.shuffle()`：

| 原始可用样本数 | 集合策略 | 后果 |
| --- | --- | --- |
| `<= 20` | 所有样本训练，验证集为空 | 无验证 F1 和早停；每 5 个 epoch 或最后一轮定期保存。 |
| `> 20` | 前 80% 训练，后 20% 验证 | 综合 F1 决定最佳模型与早停。 |
| 训练子集 `< 30` | 对已打乱的训练样本重复、再次打乱并截到 30 条 | 只增加训练步数，不增加信息量，过拟合风险仍高。 |

若动态 schema 尚未包含 NER 或 RE 标签，训练器会从训练数据的实体和关系类型集合重建 ID 映射；正常 Label Studio 工作流中，schema 应已在模型初始化时完成同步。

#### 步骤 4：token 化与 NER 标签对齐

`NERREDataset` 对每条文本执行 tokenizer，启用 truncation、`MAX_LENGTH` 和 `return_offsets_mapping`。对于一个实体字符区间 `[s,e)`，数据集寻找与该区间相交的有效 token：第一个命中的 token 写 `B-类型`，其余写 `I-类型`。未匹配 token 默认 `O`；特殊 token 和 padding 不应进入有效实体对齐。

这一步是训练中最关键的数据一致性约束：

```text
Label Studio 字符位置 -> tokenizer offset mapping -> token 下标 -> BIO label ID
```

当实体越过 `MAX_LENGTH` 截断边界、空文本、无效 start/end，或 tokenizer 的 offset 不覆盖实体时，该实体无法形成正确标签。项目使用 `do_text_preprocessing=False` 是为避免 tokenizer 改写原文导致上述映射漂移。

#### 步骤 5：RE 候选、正例与负例

数据集将可映射实体的 token 起止位置组织为关系候选。标注 relation 形成正类别；没有标注的实体对可作为类别 0“无关系”负例。负例以采样方式控制数量，避免非关系组合随实体数平方增长而淹没正关系。每个 RE 标签与对应的 `(实体1 token 范围, 实体2 token 范围)` 位置成对保存，训练时保持同一顺序。

若某条样本没有可用实体对，RE 的 labels/pairs 可为 `None`；该 batch 仍会训练 NER。若 batch 中至少有一条可用关系，所有关系标签展平为一个 tensor，并由模型按相同候选顺序生成 RE logits。

#### 步骤 6：组 batch 与动态 padding

`collate_fn` 先找出当前 batch 的最大 token 长度 `max_len`，再执行：

| 张量/字段 | 补齐值 | 原因 |
| --- | --- | --- |
| `input_ids` | `tokenizer.pad_token_id` 或 0 | 保证 token ID 合法。 |
| `attention_mask` | 0 | encoder 忽略补齐位置。 |
| `ner_labels` | -100 | CrossEntropy 的 `ignore_index`，不计损失。 |
| `re_labels` / `re_entity_pairs` | 保留 Python 列表 | 每条样本实体对数量不同，不能直接堆叠为规则矩阵。 |

这使 `[batch_size, max_len]` 而非 `[batch_size, MAX_LENGTH]` 进入 encoder。文本长度差异大时，建议按长度分桶是进一步优化方向，但当前代码尚未实现。

#### 步骤 7：模型构建、LoRA 和恢复

训练器创建 `ModernBERTForNERRE`：先本地加载基础 encoder，再创建随机初始化的 NER 头、RE 头和 257 行的距离嵌入表（距离 -128 到 128）。`use_lora=true` 时，将 PEFT 的 LoRA 注入 `Wqkv`、`Wo`、`Wi`。

随后 `_load_model_if_exists()` 检查 `best_model_path`：若有 `adapter_config.json`，加载 adapter 和 `classification_heads.pt`；若有 `checkpoint.pt`，还可恢复 optimizer、scheduler、已训练 epoch 与 best F1。恢复时仍以当前 schema 的标签维度为准；人为复制不匹配 schema 的目录可能导致状态字典维度错误或语义错配。

#### 步骤 8：每个 batch 的前向与反向传播

一个 batch 的核心操作顺序为：

```text
model.train()
input_ids / attention_mask / labels -> device
autocast（仅 CUDA）
  -> encoder 输出 sequence_output
  -> NER 头得到 [B,L,C_ner] logits
  -> 若有关系对，RE 头得到 [关系对数,C_re] logits
  -> 加权联合交叉熵 loss
GradScaler.scale(loss).backward()（CUDA）或 loss.backward()
clip_grad_norm_(model.parameters(), max_grad_norm)
optimizer.step(); scheduler.step(); optimizer.zero_grad()
```

CUDA 下 `GradScaler` 在缩放梯度后再执行梯度裁剪；CPU 下不启用 AMP。学习率调度器每一步更新，因此 warmup 和衰减的时间单位是 optimizer step，不是 epoch。训练日志报告 epoch 平均 loss。

#### 步骤 9：验证、保存与早停

有验证集时，`evaluate()` 设为 `model.eval()` 和 no-grad，计算验证 loss、NER F1、RE F1、关系正类 F1 与“无关系”准确率。用于模型选择的 `current_f1 = ner_f1 + re_f1`，并非两者平均值。

- `current_f1 > best_f1_with_delta + early_stopping_min_delta`：保存 LoRA adapter、分类头、checkpoint，更新最佳分数并将 patience 清零。
- 仅有微小提升或无提升：patience 加一；即使 `current_f1` 大于历史 best 但没有超过 min delta，也不写“最佳模型”。
- patience 达到阈值：立即提前结束。
- 无验证集：第 5、10、15、20 轮及最后一轮保存，`best_f1` 不具备验证集意义。

#### 步骤 10：训练后切换

训练正常返回后，`ModernBERTModel.fit()` 将 `self._model` 置空，清空类级 LRU 缓存，再调用 `_load_model()`。因此后续请求按新 `best_model` 加载。若训练抛异常，代码记录完整异常日志；旧的已加载模型与已存在产物不会由该异常路径主动删除。

## 5. 模型加载、schema 与缓存

### 5.1 初始化顺序

1. API 从请求取得 `project_id`、`label_config`。
2. `ModernBERTModel.setup()` 从 SDK 标签接口解析 `<Labels>` 和 `<Relation>`；SDK 解析失败时回退 XML 解析。
3. 根据 NER/RE 标签列表计算 schema ID，并将路径切换为 `output/{base_model}/{schema}/best_model`。
4. 延迟加载共享 tokenizer；基础模型与 tokenizer 均使用 `local_files_only=True`、`trust_remote_code=True`。
5. 按 PyTorch CUDA 可用性选择 `cuda` 或 `cpu`。
6. 以“全参数模型 > LoRA 模型 > 基础模型”的优先级加载，随后迁移到目标设备并调用 `eval()`。

未得到实体 schema 时，业务代码会跳过任何默认微调模型，只加载基础模型。这是防止分类头输出维度与项目标签映射不一致的保护。

### 5.2 三种加载分支

| 条件 | 加载行为 | 必需文件 |
| --- | --- | --- |
| 有 `pytorch_model.bin` | `from_pretrained()` 创建网络并加载全部状态字典 | `pytorch_model.bin`，可选 `model_config.json` |
| 有 `adapter_config.json` 和 `classification_heads.pt` | 加载基础 encoder，注入 `PeftModel` adapter，再加载 NER/RE 头和距离嵌入 | adapter 配置/权重及 `classification_heads.pt` |
| 两者均无 | 加载基础 encoder，任务头随机初始化 | 本地基础模型完整文件 |

业务模型构造后显式转换 encoder 为 float32。即使基础模型配置中 `torch_dtype` 是 bfloat16，当前实现依然以 float32 加载；CPU 兼容性更高，但 GPU 显存/吞吐可能不如 bf16/fp16，需要实测。

### 5.3 LRU 缓存

缓存 key 包括基础模型名与路径、最佳模型路径、标签列表与数量、设备、产物文件大小和修改时间。产物变更、schema 变更或设备变更会形成新 key，避免错误复用。

`MODEL_CACHE_MAX_SIZE=1` 时仅保留最近模型。设为 0 会禁用缓存；增大可服务多个 schema，但会按模型数增加内存/显存。缓存只存在当前 Python 进程，重启或多 worker 不共享。

## 6. 预测与 Label Studio 结果

### 6.1 文本字段与流程

服务优先由 `<Labels>` 绑定的 `<Text value="$字段名">` 定位任务文本，失败时回退 `text` 与 `label_studio_text`。推荐在标签配置中显式绑定，以免多字段任务取错文本。

```text
task.data text
  -> tokenizer（截断 + offset mapping）
  -> ModernBERT encoder
  -> BIO logits -> 实体解码 -> NER 阈值
  -> 有序实体对 -> RE logits -> RE 阈值
  -> 字符距离过滤
  -> token offset 回写字符 offset
  -> Label Studio labels / relation result
```

### 6.2 返回字段

实体使用 `id=ent_序号`，`from_name` 是 Labels 控件名，`to_name` 是 Text 控件名。`value.start/end/text/labels` 均针对原始文本。关系使用预测实体的 `from_id`、`to_id` 和关系标签。

任务级 `PredictionValue.score` 在当前实现中取所有实体/关系结果的最小 score；没有结果时为 2.0。该无结果值是代码的结果结构默认值，不应被解释为概率或模型置信度。

#### 6.2.1 同一示例的预测中间结果与回写

沿用 4.1.1 的文本和标签。假设模型 argmax 后预测出相同的 BIO 序列，药物四个 token 的所选标签概率为 `0.95、0.93、0.91、0.94`，症状两个 token 的概率为 `0.88、0.90`。实体置信度分别是 `0.9325` 和 `0.8900`。RE 头预测药物 -> 症状为“不良反应”，概率 `0.8700`。

NER/RE 模型的中间结果仍使用 **token 下标** 和内部 ID：

```json
{
  "entities":[
    {"id":"entity_0","start":5,"end":9,"label":"药物","score":0.9325},
    {"id":"entity_1","start":12,"end":14,"label":"症状","score":0.8900}
  ],
  "relations":[
    {"from_id":"entity_0","to_id":"entity_1","type":"不良反应","confidence":0.8700}
  ]
}
```

`predict_text()` 用 `offset_mapping[5][0]` 和 `offset_mapping[8][1]` 将药物改成字符 `[4,8)`；用 `offset_mapping[12][0]` 和 `offset_mapping[13][1]` 将症状改成 `[11,13)`。关系字符间距为 `max(4,11) - min(8,13) = 3`，小于默认 `RE_MAX_DISTANCE=50`，所以该关系保留。

业务层会把内部 `entity_0`、`entity_1` 改为新的 Label Studio 结果 ID，而不是复用训练标注的 `ls_drug_1`：

```text
entity_ls_id_map = {"entity_0": "ent_0", "entity_1": "ent_1"}
```

最终返回给 Label Studio 的 `result` 数组：

```json
[
  {
    "id":"ent_0", "from_name":"label", "to_name":"text", "type":"labels",
    "value":{"start":4,"end":8,"text":"阿司匹林","labels":["药物"]}, "score":0.9325
  },
  {
    "id":"ent_1", "from_name":"label", "to_name":"text", "type":"labels",
    "value":{"start":11,"end":13,"text":"皮疹","labels":["症状"]}, "score":0.8900
  },
  {
    "type":"relation", "from_id":"ent_0", "to_id":"ent_1",
    "labels":["不良反应"], "score":0.8700
  }
]
```

任务级 `PredictionValue.score` 是三项结果中的最小值 `0.8700`。完整 ID 链路为：`ls_drug_1`（人工标注）-> `entity_0`（模型中间结果）-> `ent_0`（预测响应），它们指向同一实体但用途不同。

### 6.3 端到端预测详细过程

预测请求可以包含多个 task；每个任务独立执行以下过程。模型对象可能每次请求创建，但权重对象会通过 LRU 缓存复用。

```text
POST /predict
  -> 读取 project 与 label_config，解析 schema
  -> 命中缓存或加载基础/LoRA/全参模型，model.eval()
  -> 从 task.data 解析原文文本
  -> tokenizer + offset mapping + 截断
  -> encoder 前向（no_grad）
  -> NER softmax / argmax / BIO 合并 / 实体阈值
  -> 枚举实体有序对并执行 RE softmax / 阈值
  -> token 下标转字符偏移、字符距离过滤
  -> Label Studio labels/relation 结构与任务 score
  -> API 包装为 {"results": [...]}
```

#### 步骤 1：请求上下文与模型准备

API 层从 body 读取 `tasks`、`label_config`、`project` 和 `params`。`project` 被转换为项目 ID，`label_config` 用于重新建立标签 ID 和 schema 路径。业务模型的缓存 key 同时含标签序列、产物签名与设备，因此相同请求通常命中，同一基础模型但不同 schema 或训练产物修改后会重新加载。

无论加载哪个分支，模型都会迁移到 `cuda` 或 `cpu` 并调用 `eval()`；真正的 `model.predict()` 处于 `torch.no_grad()` 中，因此预测不会保留反向传播图，也不会更新权重。

#### 步骤 2：文本提取与输入编码

`_extract_task_text()` 按标签配置推导的字段名逐一读取 `task.data`，然后回退 `text`、`label_studio_text`。找不到非空文本时该 task 被跳过，不产生 PredictionValue。

找到文本后，`predict_text()` 调用 tokenizer：

```text
padding = false
truncation = true
max_length = MAX_LENGTH
return_tensors = "pt"
return_offsets_mapping = true
```

预测不 padding 到固定长度，因此单条输入的计算量由实际 token 数决定。`input_ids`、`attention_mask` 会迁移到模型设备；offset mapping 保留在 CPU，用于后续转换。文本 token 数超过 `MAX_LENGTH` 时，尾部文本没有 logits，也不会产生实体或关系。

#### 步骤 3：NER 前向、解码与阈值

encoder 前向生成 `[1,L,1024]`，NER 头产生 `[1,L,C_ner]`。对最后一维做 softmax 获得每个 token 的标签概率，argmax 获得标签 ID。解码器按 BIO 状态机串联实体，并忽略 `attention_mask=0` 的 padding。

对每个解码出的 token 实体，代码收集其 token 区间内“被预测标签”的 softmax 概率并计算平均值。例如三个 token 的概率为 0.8、0.6、0.9，则实体 score 为 `(0.8+0.6+0.9)/3 = 0.7667`。低于 `NER_THRESHOLD` 的实体在 RE 候选生成**之前**删除，因此 NER 阈值也会间接减少关系召回。

#### 步骤 4：RE 候选与关系判定

剩余实体重新赋 ID（`entity_0`、`entity_1` 等），模型双重遍历实体：`i != j` 且实体标签不同才生成候选。因此：

- 方向敏感：药物 -> 症状 与 症状 -> 药物都可能进入模型；
- 同类型实体对当前被跳过，即使业务上可能存在同类型关系；
- 少于两个实体时完全跳过 RE 头；
- 候选列表顺序与 logits 生成顺序一致，保证结果可回填到原实体。

RE 头对每对输出 softmax。预测 ID 为 0 时不输出；非 0 的最大概率达到 `RE_THRESHOLD` 时写入 `from_id`、`to_id`、`type` 和 `confidence`。之后将 token 实体区间转为字符区间，并以两实体字符区间的间隔 `gap = max(start1,start2) - min(end1,end2)` 过滤大于 `RE_MAX_DISTANCE` 的关系；设定为 0 或负值则不做此过滤。

#### 步骤 5：token 偏移转回 Label Studio 字符偏移

NER 解码初始 `start/end` 是 token 下标。对实体 token 范围 `[ts,te)`：

```text
character_start = offset_mapping[ts][0]
character_end   = offset_mapping[te - 1][1]
```

以该区间从原文重新切出 `text[start:end]`，而不是相信 tokenizer 还原文本。特殊 token 的 offset 通常为零区间；正常实体不应落在此类 token 上。此映射要求请求的原文与标注/前端展示文本完全相同。

#### 步骤 6：组装响应与失败行为

每个实体转为 `type="labels"`，每个关系转为 `type="relation"`。实体 `from_name` 根据 Label Studio Labels 控件映射，`to_name` 取绑定 Text 控件名；如果无法解析 Text 控件名则使用 `text` 作为回退。结果中的 score 会四舍五入到 4 位小数。

常见的预测结果与含义如下：

| 现象 | 当前行为 | 排查方向 |
| --- | --- | --- |
| `results` 为空或少于 tasks | 文本字段为空/未解析的 task 会被跳过 | 检查 `<Text value>` 与 task.data 的字段名。 |
| 有实体无关系 | 少于两实体、候选被同类型规则跳过、RE 预测为 0、置信度/距离过滤 | 分别查看 NER、RE 阈值、实体标签组合和 `RE_MAX_DISTANCE`。 |
| 位置高亮错误 | 字符串被前端/导入过程改写，或 tokenizer offset 对齐不一致 | 对比请求原文、Label Studio start/end 与日志 token 数。 |
| 首次请求慢 | 冷加载基础模型、adapter 或 tokenizer | 保持合理的 `MODEL_CACHE_MAX_SIZE`，预热常用 schema。 |
| GPU 未生效 | `torch.cuda.is_available()` 为 false | 检查 NVIDIA 驱动、Docker GPU 透传和 GPU Compose 配置。 |

## 7. Label Studio 交互原理

### 7.1 时序

```text
Label Studio                         ML Backend
     | POST /setup (schema, token)       |
     |---------------------------------->| 解析标签，Token 按项目 ID 存内存
     |<----------------------------------| model_version
     | POST /predict                     |
     |---------------------------------->| 加载/复用对应 schema，返回 results
     |<----------------------------------|
     | POST /webhook START_TRAINING      |
     |---------------------------------->| SDK 下载已标注任务，训练、保存、重载
     |<----------------------------------| 201 status=ok
```

### 7.2 `/setup`

请求包含 `project`、`schema`、可选 `extra_params`、`access_token`。服务从形如 `项目ID.时间戳` 的 project 字段提取项目 ID，初始化模型并将 Token 放入模块级字典 `_LABEL_STUDIO_ACCESS_TOKENS[project_id]`。Token 不落盘，且请求日志会脱敏 `access_token`、`api_key`、`authorization`、`cookie`、`password` 等字段。

因此容器重启后 Token 会丢失。操作人员应在 Label Studio 项目中重新保存/刷新 ML Backend 连接，以触发新的 `/setup`。当前 Compose 以单进程使用最安全；改为 Gunicorn 多 worker 后每个 worker 都有独立 Token 字典，不能直接沿用此机制。

### 7.3 `/predict`

请求必须包含 `tasks`、`project`、`label_config`；可有 `params.context`。API 每次创建业务模型对象，但底层模型可以命中进程内 LRU 缓存。返回格式是 `{"results": [...]}`。若设置 `BASIC_AUTH_USER` 与 `BASIC_AUTH_PASS`，全部接口要求 HTTP Basic Auth。

### 7.4 `/webhook` 和训练触发

HTTP 层识别 `ANNOTATION_CREATED`、`ANNOTATION_UPDATED`、`ANNOTATION_DELETED`、`START_TRAINING`。但业务 `fit()` 当前只执行 **`START_TRAINING`**；其他事件会被记录为跳过训练。因此新增或编辑标注不会自动增量训练，需在 Label Studio 中显式启动训练。

训练时使用 `/setup` 缓存 Token 和 `LABEL_STUDIO_URL` 创建 SDK 客户端，调用 `tasks.list(project=..., only_annotated=True, fields="all")`。若 Token 不存在、连接失败或没有有效实体样本，训练直接告警并返回。

### 7.5 推荐标签配置

```xml
<View>
  <Labels name="label" toName="text">
    <Label value="药物"/>
    <Label value="症状"/>
  </Labels>
  <Text name="text" value="$text"/>
  <Relations>
    <Relation value="不良反应"/>
  </Relations>
</View>
```

实体标签来自 `<Labels>` 下的 `<Label value>`，关系标签来自 `<Relation value>`。标签内容或顺序改变会产生不同 schema ID，旧模型不会被静默复用。

### 7.6 HTTP 接口契约

| 接口 | 方法 | 关键输入 | 成功响应 | 当前用途 |
| --- | --- | --- | --- | --- |
| `/health`、`/` | GET | 无 | `{"status":"UP","model_class":"ModernBERTModel"}` | 存活检查。 |
| `/setup` | POST | `project`、`schema`、`access_token`、可选 `extra_params` | `{"model_version":"..."}` | 初始化项目标签、下发训练拉取所需 Token。 |
| `/predict` | POST | `tasks`、`project`、`label_config`、可选 `params.context` | `{"results":[...]}` | 对任务文本预测实体与关系。 |
| `/webhook` | POST | `action`、`project.id`、`project.label_config` | HTTP 201，`{"status":"ok"}` | Label Studio 触发训练事件。 |
| `/metrics` | GET | 无 | `{}` | 占位接口，当前没有 Prometheus 指标。 |

`/predict` 的最小请求示例：

```json
{
  "project": "104.1710000000",
  "label_config": "<View>...</View>",
  "tasks": [
    {"id": 1, "data": {"text": "患者服用阿司匹林后出现皮疹"}}
  ],
  "params": {"context": {}}
}
```

`project` 在 API 层按第一个英文句点切分，前半部分作为项目 ID。`label_config` 用于每次预测建立正确的标签映射和 schema 路径；不能省略，否则模型可能只加载基础权重。`tasks` 中没有解析到文本字段的任务会被跳过，因此返回结果数量可能少于输入任务数，调用方应按任务内容而不是数组位置盲目对应。

## 8. 参数说明

### 8.1 运行环境参数

| 参数 | 默认值 | 含义与调参影响 |
| --- | --- | --- |
| `ML_BACKEND_PORT` | 9090 | 宿主机到容器的端口映射；容器内始终监听 9090。 |
| `BASE_MODEL_NAME` | `chinese-modernbert-large-wwm` | 基础模型目录名，必须对应 `/app/bert-base-model/{名称}`。 |
| `MAX_LENGTH` | 1024 | token 上限。增大保留更多上下文但显著增加注意力计算和内存；超长文本尾部被截断。 |
| `MODEL_CACHE_MAX_SIZE` | 1 | 进程内缓存模型数；0 关闭，较大值以更高内存换多 schema 首次加载速度。 |
| `NER_THRESHOLD` | 0.5 | 实体平均 token 概率下限。提高减少误报，降低会提高召回。 |
| `RE_THRESHOLD` | 0.5 | 关系概率下限。应与 NER 阈值一起在验证集校准。 |
| `RE_MAX_DISTANCE` | 50 | 输出关系最大字符间距；小于等于 0 关闭过滤。 |
| `LABEL_STUDIO_URL` | `http://host.docker.internal:8080` | 必须从容器可访问的 Label Studio 根地址。 |
| `TRANSFORMERS_OFFLINE` / `HF_HUB_OFFLINE` | 1 | 禁止在线下载，模型文件不完整会加载失败。 |
| `TOKENIZERS_PARALLELISM` | false | 避免 tokenizer 多进程并行警告和竞争。 |
| `OMP_NUM_THREADS` / `MKL_NUM_THREADS` | 4（示例） | CPU 线程数上限；高并发时过大可能造成线程争抢。 |
| `DNNL_MAX_CPU_ISA` / `ONEDNN_MAX_CPU_ISA` | 空 | 老 CPU 出现非法指令时可限制 oneDNN ISA，代价是性能下降。 |
| `DISABLE_MKLDNN` | 0 | 禁用 MKLDNN 的兼容性开关，通常不建议常态启用。 |

### 8.2 GPU 构建参数

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `GPU_BASE_IMAGE` | `nvidia/cuda:12.6.3-devel-ubuntu24.04` | GPU 基础镜像，devel 版含 `nvcc`，用于源码编译 Flash Attention 2。 |
| `GPU_PYTORCH_INDEX_URL` | `https://download.pytorch.org/whl/cu126` | CUDA 12.6 PyTorch wheel 索引。 |
| `GPU_PYTORCH_VERSION` | 2.7.1 | GPU PyTorch 精确版本。 |
| `NVIDIA_VISIBLE_DEVICES` | all | 暴露给容器的 GPU，可指定编号。 |
| `NVIDIA_DRIVER_CAPABILITIES` | `compute,utility` | 所需驱动能力。 |

默认 CPU 构建使用 `python:3.12-slim` 和 CPU PyTorch；GPU 覆盖 Compose 注入 CUDA devel 基础镜像、CUDA PyTorch 索引和 `INSTALL_FLASH_ATTN=true`。Flash Attention 2 只在 GPU 构建安装。CPU/GPU 默认共用 `modern-bert-fine-tuning:latest` 标签，需同时保存时应额外打 `:cpu` 和 `:gpu-cu126` 标签。

### 8.3 通用构建参数

| 参数 | 默认值 | 作用与约束 |
| --- | --- | --- |
| `PIP_INDEX_URL` | `https://mirrors.aliyun.com/pypi/simple`（示例环境） | 安装一般 Python 依赖的包索引。网络受限时可替换为组织内部可信镜像。 |
| `PYTORCH_INDEX_URL` | `https://download.pytorch.org/whl/cpu` | CPU PyTorch 的专用 wheel 索引。 |
| `PYTORCH_FIND_LINKS` | 空 | 若设置则用作 pip 的 `-f` 链接源，并优先于 PyTorch 专用索引路径。 |
| `PYTORCH_VERSION` | 2.7.1 | CPU PyTorch 精确版本；不可随意改成范围约束，否则镜像可复现性下降。 |
| `BASE_IMAGE` | `python:3.12-slim` | Dockerfile 默认基础镜像；GPU Compose 用 CUDA devel 镜像覆盖。 |
| `INSTALL_FLASH_ATTN` | false | Dockerfile 条件开关；仅 GPU Compose 设为 true，因此 CPU 镜像不带 Flash Attention 扩展。 |

Dockerfile 对 CUDA devel 镜像单独创建 `/opt/venv`。这是因为 Ubuntu 系统 Python 受 PEP 668 管理，不能直接向系统 site-packages 执行 pip 写入；`PATH` 优先使用虚拟环境，CPU 官方 Python 镜像则仍使用自带解释器。

### 8.4 训练默认参数

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `epochs` | 20 | 最大轮数，早停可能提前结束。 |
| `batch_size` | 4 | 每步样本数；增大提升吞吐但提高显存。 |
| `learning_rate` | 5e-5 | encoder/LoRA 学习率；过大可能遗忘预训练知识。 |
| `classifier_lr` | 5e-4 | 分类头和距离嵌入学习率，默认较基础学习率大 10 倍。 |
| `warmup_ratio` | 0.1 | 初始 10% 步数线性 warmup。 |
| `weight_decay` | 0.01 | AdamW 权重衰减，降低过拟合。 |
| `max_grad_norm` | 1.0 | 梯度范数裁剪阈值。 |
| `hidden_dropout_prob` | 0.1 | NER/RE 分类头 dropout。 |
| `ner_loss_weight` / `re_loss_weight` | 1.0 / 2.0 | 联合损失权重，默认强化较稀疏的 RE 信号。 |
| `early_stopping_patience` | 5 | 无实质改善可连续容忍的验证轮数。 |
| `early_stopping_min_delta` | 0.001 | 认定综合 F1 有实质提升的最小差。 |
| `lora_r` / `lora_alpha` | 16 / 32 | LoRA 秩和缩放，决定适配器容量。 |
| `lora_dropout` | 0.1 | LoRA 分支正则化。 |
| `lora_target_modules` | Wqkv, Wo, Wi | 注入适配器的 ModernBERT 模块名称。 |

## 9. 部署、验收和风险

### 9.1 持久化边界

| 位置 | 内容 | 是否持久化 |
| --- | --- | --- |
| `bert-base-model` 只读挂载 | 基础权重、tokenizer、remote code | 必须。 |
| `output` 读写挂载 | adapter、任务头、checkpoint | 必须，容器重建后仍需推理/续训。 |
| 模型 LRU 缓存 | 已加载的 Python 对象 | 否，进程重启即失效。 |
| 动态 Token 缓存 | `project_id -> access_token` | 否，必须通过 `/setup` 刷新。 |
| `cache.db` | 基类项目配置缓存 | 可持久化，但不含动态 Token。 |

### 9.2 验收建议

1. 检查基础模型目录含 `config.json`、`model.safetensors`、tokenizer 文件和 custom tokenizer 代码。
2. `GET /health` 返回 `status=UP`，但不要将其等同于某 schema 模型已加载。
3. 在 Label Studio 保存 ML Backend 配置，确认 `/setup` 成功返回模型版本。
4. 以包含多个实体与关系的短文本调用 `/predict`，检查 Label Studio 高亮位置与原文完全一致。
5. 启动 `START_TRAINING`，检查对应 schema 目录产生 adapter 与 `classification_heads.pt`，并验证训练后预测能加载新产物。
6. 重启服务后重新保存 ML Backend 连接，确认 Token 刷新并可再次训练。
7. GPU 环境额外验证 `torch.cuda.is_available()` 和 Flash Attention CUDA 算子；CPU 环境验证目标指令集兼容性。

### 9.3 风险清单

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 标签 schema 修改 | 新 schema 目录冷启动，旧模型不复用。 | 标签变更纳入版本管理并安排重新训练。 |
| 长文本截断 | 尾部实体和关系不参与训练/预测。 | 先统计 token 长度；必要时实现分段和合并。 |
| 实体数过多 | RE 有序候选接近 O(E^2)，时延增加。 | 校准 NER 阈值和距离，增加候选类型约束。 |
| 少样本过拟合 | 过采样无法创造信息，F1 波动大。 | 增加高质量标注，保留独立测试集。 |
| Token 丢失/多 worker | 训练拉取任务失败。 | 重启后刷新 `/setup`；扩展时使用受控共享凭证方案。 |
| 同步训练 | 训练会占用服务处理能力。 | 生产环境将训练迁移到队列/独立 worker。 |
| `trust_remote_code=True` | 本地模型目录 Python 代码可执行。 | 仅使用受控来源模型，校验版本和哈希。 |
| 基准脚本凭证 | `predict_test.py` 不应保存真实 Cookie。 | 使用环境变量/密钥管理；已暴露的会话应立即轮换。 |
